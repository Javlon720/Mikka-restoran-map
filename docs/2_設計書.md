## 1. システム全体構成
本システムは、保守性と拡張性を高めるため、フロントエンドとバックエンドを一つのリポジトリで管理する **NPM workspaces モノレポ構成** を採用しています。
バックエンドは **クリーンアーキテクチャ (Clean Architecture)** に基づき設計されており、データベースには **PostgreSQL** を使用しています。フロントエンドは **Vite** を用いた高速なビルド環境のもと、Vanilla JS、HTML、CSS で構築されています。

### ディレクトリ構成
```
Jdu/
├── packages/
│   ├── backend/          # バックエンド (Node.js, TypeScript, Fastify)
│   │   ├── src/
│   │   │   ├── domain/         # エンティティ定義、リポジトリI/F (コア領域)
│   │   │   ├── use-cases/      # ビジネスロジック (ユースケース)
│   │   │   ├── adapters/       # コントローラー、リポジトリ実装 (データベース接続)
│   │   │   └── infrastructure/ # サーバー起動、ルーター、ミドルウェア
│   │   └── db.sql              # データベーススキーマと初期データ
│   └── frontend/         # フロントエンド (HTML, CSS, JS, Vite)
│       ├── index.html          # メインのHTML
│       ├── css/styles.css      # スタイルシート
│       └── js/                 # アプリケーションロジック (i18n, API通信, 地図)
```

## 2. バックエンド設計（クリーンアーキテクチャ）
依存ルールに基づき、内側のレイヤー（Domain）が外側のレイヤー（Infrastructure）に依存しないよう設計されています。

1. **Domain Layer (コア):**
   - `entities/`: ビジネスモデル (`User`, `Restaurant`, `Review`)
   - `repositories/`: データベースアクセスのためのインターフェース定義（インターフェースのみで、実装は持たない）
2. **Use Case Layer:**
   - アプリケーション固有のビジネスロジック。例：`CreateRestaurant`, `LoginUser`, `CreateReview`, `GetGeminiResponse` などのクラス。
3. **Adapters Layer:**
   - `controllers/`: HTTPリクエストを受け取り、ユースケースを実行し、レスポンスを返す (`UserController`, `RestaurantController`, `ReviewController`, `ChatController`)
   - `repositories/pg/`: PostgreSQLを利用して、Domain LayerのRepositoryインターフェースを実際に実装したクラス (`PgUserRepository`, `PgRestaurantRepository`, `PgReviewRepository`)
4. **Infrastructure Layer:**
   - Fastifyサーバー設定、ルーティング定義 (`router.ts`)、認証ミドルウェア、ファイルアップロード処理 (`multer`)。

## 3. データベース設計（PostgreSQL）
データベースには、以下の3つの主要なテーブルがあります。

### 3.1 `users` テーブル (ユーザー情報)
ユーザーの認証情報と権限（管理者か一般ユーザーか）を管理します。

| カラム名 | データ型 | 制約 | 説明 |
| :--- | :--- | :--- | :--- |
| `id` | SERIAL | PRIMARY KEY | ユーザー固有ID |
| `username` | VARCHAR(50) | UNIQUE, NOT NULL | ユーザー名 |
| `email` | VARCHAR(100) | UNIQUE, NOT NULL | メールアドレス |
| `password_hash` | VARCHAR(255) | | パスワードハッシュ（Googleログイン時はNULL可） |
| `role` | VARCHAR(20) | DEFAULT 'user' | 権限 (`admin` または `user`) |
| `created_at` | TIMESTAMP | DEFAULT CURRENT_TIMESTAMP | 登録日時 |

### 3.2 `restaurants` テーブル (飲食店情報)
飲食店の基本情報と地図表示のための緯度・経度、画像パスを管理します。

| カラム名 | data型 | 制約 | 説明 |
| :--- | :--- | :--- | :--- |
| `id` | SERIAL | PRIMARY KEY | 飲食店固有ID |
| `name` | VARCHAR(100) | NOT NULL | 店舗名 |
| `cuisine` | VARCHAR(50) | NOT NULL | 料理ジャンル |
| `address` | TEXT | NOT NULL | 住所 |
| `description` | TEXT | | 店舗の説明 |
| `image_url` | TEXT | | 店舗画像へのパス |
| `latitude` | DECIMAL(9,6) | NOT NULL | 地図表示用の緯度 |
| `longitude` | DECIMAL(9,6) | NOT NULL | 地図表示用の経度 |
| `created_at` | TIMESTAMP | DEFAULT CURRENT_TIMESTAMP | 登録日時 |

### 3.3 `reviews` テーブル (口コミ情報)
飲食店に対する評価、コメント、画像パスを管理します。

| カラム名 | data型 | 制約 | 説明 |
| :--- | :--- | :--- | :--- |
| `id` | SERIAL | PRIMARY KEY | 口コミ固有ID |
| `restaurant_id` | INT | FOREIGN KEY (restaurants.id) ON DELETE CASCADE | 対象店舗ID |
| `user_id` | INT | FOREIGN KEY (users.id) ON DELETE CASCADE | 投稿ユーザーID |
| `rating` | INT | CHECK (rating >= 1 AND rating <= 5) | 評価点 (1〜5星) |
| `comment` | TEXT | NOT NULL | コメント本文 |
| `image_url` | TEXT | | 口コミ画像へのパス |
| `created_at` | TIMESTAMP | DEFAULT CURRENT_TIMESTAMP | 投稿日時 |

## 4. API エンドポイント設計

### 4.1 認証系 (`/auth`)
- `POST /auth/register` : 新規ユーザー登録
- `POST /auth/login` : ログイン（JWTをCookieにセット）
- `POST /auth/google` : Googleアカウントでのログイン
- `POST /auth/logout` : ログアウト（Cookieを削除）

### 4.2 飲食店系 (`/restaurants`)
- `GET /restaurants` : 全店舗一覧取得（キーワード検索対応）
- `GET /restaurants/:id` : 店舗詳細取得
- `POST /restaurants` : 店舗追加（管理者権限が必要、画像アップロード対応）
- `PUT /restaurants/:id` : 店舗情報編集（管理者権限が必要、画像アップロード対応）
- `DELETE /restaurants/:id` : 店舗削除（管理者権限が必要）

### 4.3 口コミ系 (`/reviews`)
- `GET /restaurants/:restaurantId/reviews` : 特定店舗の口コミ一覧取得
- `POST /reviews` : 新規口コミ投稿（ログインが必要、画像アップロード対応）
- `PUT /reviews/:id` : 口コミの編集（投稿者本人または管理者のみ）
- `DELETE /reviews/:id` : 口コミの削除（投稿者本人または管理者のみ）

### 4.4 AI チャット (`/chat`)
- `POST /chat` : Mikka AI Assistant への質問送信。バックエンドから Gemini API を呼び出し、現在の飲食店リスト情報をコンテキストとして渡して、最適な店舗提案を返します。

## 5. フロントエンド設計と多言語化
フロントエンドは Single Page Application (SPA) 的な挙動をし、モーダルウィンドウを多用することでスムーズな操作感を実現しています。

### 多言語化の仕組み (`js/i18n.js`)
UIの表示切り替えのために、自作の翻訳ライブラリを実装しています。
1. 各言語の翻訳文を `translations` オブジェクトに辞書形式で定義。
2. HTML内の翻訳対象要素に `data-i18n="キー名"` や `data-i18n-placeholder="キー名"` 属性を付与。
3. 言語切り替え時に、JavaScriptでDOMをトラバースして要素のテキストやプレースホルダーを動的に書き換え。
4. 選択された言語（`uz`, `en`, `ru`, `ja`）はブラウザの `localStorage` に保存され、リロード後も維持されます。
